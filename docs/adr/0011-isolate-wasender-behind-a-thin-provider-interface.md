# Isolate Wasender behind a thin provider interface

Keep session lifecycle, directory synchronization, text sending, media retrieval, and webhook normalization behind a small internal WhatsApp provider contract with one Wasender implementation. Raw Wasender payloads, credentials, event names, status values, and errors do not escape the adapter into domain records, MCP contracts, or product copy. Calls use operation-specific ambiguity classes rather than a generic retry wrapper: JSON reads have 10-second attempts and at most three jittered attempts within 25 seconds for network errors, `408`, `429`, and `5xx`; text sends have one 15-second attempt and never retry an ambiguous result; lifecycle writes have 15-second attempts and reconcile provider state before another side effect; media-decrypt metadata calls have 30 seconds and guarded media downloads have 60 seconds. `get_send_status` reads only the locally converged Send Operation established by its causally bound complete direct response and later webhook evidence exactly correlated under ADR 0017's same-connection, shared-stable-identifier rule; it never polls Wasender's message-info endpoint, whose behavior depends on provider identifiers, message logging, and undocumented retention. Responses are byte-bounded, bounded `Retry-After` is honored, deletion repeats only after reconciliation until absence, and metrics contain no content. This preserves a viable replacement seam given Wasender's undocumented guarantees and unofficial WhatsApp relationship, without building runtime provider selection or a speculative plugin system.
