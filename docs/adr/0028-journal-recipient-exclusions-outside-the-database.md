# Journal WhatsApp Recipient Exclusions outside the database

A WhatsApp Recipient Exclusion must remain effective after Neon is restored to a point before the User set it, so Neon alone cannot be its authority. Every acknowledged transition is therefore also an append-only object in a dedicated private R2 bucket under an indefinite bucket-lock rule, using the same restore-external pattern as deletion markers but a separate purpose-specific HMAC key. The journal prefix is a non-reversible HMAC over environment, WhatsApp Connection identity, recipient kind, and stable connection-scoped recipient locator; object bodies contain only version, transition identity, desired excluded state, effective time, and the greatest permanent purge cutoff, with no tenant identifier, connection identifier, public handle, provider identifier, name, phone data, content, or credential. Writes follow prepare, append, finalize: Neon prepares one stable idempotent transition under the Personal Account and WhatsApp Connection row locks, the API appends the byte-stable object with create-if-absent semantics, and only then does Neon finalize current state, purge readable history, and let the API answer. A byte-identical object at an existing key is an idempotent replay; different bytes are an integrity failure; a transition prepared but never acknowledged is completed by a bounded scheduled process. After a restore the coordinator enumerates restored recipient identities, derives their prefixes, replays every ordered transition, reapplies each greatest purge cutoff whether or not the recipient is currently excluded, and drains Stored Media object deletions; any malformed object, replay failure, or unresolved prepared transition keeps the readiness gate closed. Re-enable therefore restores future eligibility without ever restoring purged content, and broader Connection or Personal Account deletion evidence stays authoritative and terminal.
