# Keep authoritative quota reservations in Neon

Use a tenant-scoped Neon quota ledger as the authority for send frequency, message-read records, decrypted-media bytes, retained-media usage, and request frequency. Each operation locks affected subjects in deterministic order and conditionally reserves every applicable unit in the same transaction as its Activity Log and, for a new send, its Send Operation; idempotent send replays do not consume quota again. MCP and API callers share Personal Account request, send, returned-record, and media-byte quotas. API callers also reserve per-API-Key request frequency in that same Neon transaction. Edge state is never authoritative. For a new send, that transaction also creates the idempotency binding, sets `processing`, anchors `attempt_claimed_at` at the database insertion after any encrypted file snapshot, sets `lease_expires_at` 45 seconds later, and makes its commit the durable provider-attempt boundary. Failure before commit rolls back all of those records and units; after commit, send units are never refunded, including after a failed or unknown outcome. Read and media units are released only when the platform fails before any result or response body is released; once release begins, the selected record count or full verified plaintext media size commits even if the client disconnects. Validation failures, authorization failures, pre-quota rejections, and idempotent replays consume nothing. Request-frequency limits use exact rolling minute and hour windows, while daily send, returned-record, and decrypted-media limits use UTC calendar days and report the binding limit plus retry and reset times. Edge rate limiting may shed obvious abuse but cannot grant capacity, and Durable Objects are not authoritative because their otherwise strongly consistent state cannot atomically commit the corresponding Neon records without a distributed reservation protocol. Stored Media becomes quota-bearing at its queryable verified ready byte size through a conditional Personal Account usage update when processing finalizes and is released after deletion makes the object unavailable; an object that loses the finalization race remains unavailable and is removed from R2.
