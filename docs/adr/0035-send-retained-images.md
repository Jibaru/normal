# Send retained images

Add `send_image` beside `send_text_message` and `send_pdf_file`, and allow the existing REST Send Operation route to accept the same image request. A caller supplies exactly one Directory recipient or Direct Address and exactly one source: strict standard Base64 with canonical padding where required and no whitespace or data-URL prefix, or an HTTPS URL under ADR 0034's credential, port, redirect, address-resolution, timeout, and actual-byte controls. Normal accepts only bytes whose signature identifies JPEG or PNG, derives the normalized `image/jpeg` or `image/png` MIME type from that signature, and enforces an exact maximum of `5,000,000` bytes. The optional caption uses the existing SendText contract: one through 4,096 Unicode scalar values, at least one value outside Unicode 17.0 `White_Space`, and no trimming, normalization, or truncation.

Current `messages:send` authorization, selected-Connection access, and Client Confirmation apply before source retrieval. A domain-separated request-shape HMAC over the grant, Connection, destination, and operation type lets a bound key reject a changed destination before retrieval without retaining a Direct Address. An unbound request then applies destination eligibility and WhatsApp Recipient Exclusion before retrieval and again when the Send Operation commits. For a destination-compatible retained binding, verified bytes must be loaded to distinguish exact replay from changed content because neither source URLs nor plaintext bytes are retained in Neon; that path can only replay or conflict and never reserves quota or reaches the provider. Before provider access for a new send, Normal snapshots and encrypts the verified bytes as a Pending Send File and records its exact size, SHA-256 digest, and normalized image MIME with the Send Operation. The exact bytes, normalized MIME, destination, Connection, grant identity, and presence and exact UTF-8 bytes of the optional caption enter the exact-request idempotency fingerprint; the source URL does not. The file counts against the Personal Account's Stored Media quota and follows the existing Pending Send File rollback, retention, deletion, restore, and confirmed-object-deletion quota-release rules. Normal retains neither a supplied source URL nor a provider upload URL and emits neither URL, image bytes, nor caption through logs, Activity Logs, errors, or telemetry.

A committed operation performs one provider upload bounded to 10 seconds followed by at most one image-send attempt bounded to 15 seconds. Each bound covers response headers and the complete byte-bounded response body. An upload failure before the send is definitive. Ambiguous image-send acceptance becomes `unknown` and is never retried automatically. Identity-only provider evidence updates only the Send Operation and must never materialize the caption without the image. An authenticated content-bearing image upsert establishes the outbound Stored Message and supersedes the Pending Send File and caption; the pending file is not promoted into Stored Media. Neither caption nor image is reconstructed from the idempotency fingerprint after pending content expires.
